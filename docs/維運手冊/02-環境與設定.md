## wrangler.toml 解說

設定檔在 `scope3-worker/wrangler.toml`。逐段：

```toml
name = "scope3-worker"
main = "src/index.ts"
compatibility_date = "2024-12-01"
compatibility_flags = ["nodejs_compat"]   # @octokit、js-yaml 需要 Node 相容層
```

**Bindings**（程式碼用 `c.env.<binding>` 存取）：

| binding 名稱 | 種類 | 對應資源 | 程式碼用途 |
|--------------|------|----------|------------|
| `DB` | D1 | `scope3` | `c.env.DB`，所有 D1 查詢 |
| `FILES` | R2 | `scope3-files` | `c.env.FILES.put()`，存佐證檔 |
| `SUBMISSION_QUEUE` | Queue producer | `scope3-pull-jobs` | 宣告了 producer binding，但目前程式碼未呼叫（見下方注意） |

```toml
[[queues.consumers]]
queue = "scope3-pull-jobs"
max_batch_size = 10        # 每批最多 10 筆
max_batch_timeout = 30     # 最多等 30 秒湊批
```

> ⚠️ producer binding 已宣告，但程式碼中**沒有任何 `.send()`**，也**沒有 cron `[triggers]`**。佇列消費端（`handleQueue`）可運作，但目前無觸發端把工作排進佇列。

## Worker secrets 一覽表

機密用 `wrangler secret put <NAME>` 設定（不入 wrangler.toml、不入版控）。設定指令見 [04](04-維運操作.md)。

| secret | 用途 | 怎麼取得 | 備註 |
|--------|------|----------|------|
| `GITHUB_APP_PRIVATE_KEY` | 建 GitHub App JWT、換 installation token | App 設定頁 → General → Private keys → Generate（下載 `.pem`） | ⚠️ **必須是 PKCS8**（`-----BEGIN PRIVATE KEY-----`）。GitHub 下載的是 PKCS1，Workers Web Crypto 不吃，要先轉換——見 [03 案例 2](03-除錯指南.md) |
| `GITHUB_WEBHOOK_SECRET` | 驗 webhook 的 `x-hub-signature-256` HMAC 簽章 | App 設定頁 → General → Webhook → Secret（自訂，例 `openssl rand -hex 32`） | 與 App 設定頁填的值必須一致 |
| `GITHUB_APP_CLIENT_ID` | admin OAuth 授權與換 token | App 設定頁的 Client ID（即 `Iv23li8KLFZL6RUQORRz`） | 與 vars 的 `GITHUB_APP_ID` 不同，這是 OAuth 用的 |
| `GITHUB_APP_CLIENT_SECRET` | admin OAuth 換 user token | App 設定頁 → Client secrets → Generate a new client secret | 只在產生當下看得到，沒記到要重產 |
| `SESSION_SECRET` | 簽 admin session cookie 與 OAuth state（HMAC-SHA256） | 自產隨機值（`openssl rand -hex 32`） | 不需經 GitHub，自訂即可 |
| `RESEND_API_KEY` | 寄供應商邀請信（Resend） | Resend 後台 API key | **目前未設**（選用）。未設時 `syncConfig` 略過寄信，改手動遞送 `supplier-links.md` 連結——這是正常狀態 |

**目前已設定**（依 CLAUDE.md）：前 5 個（`GITHUB_APP_PRIVATE_KEY`、`GITHUB_WEBHOOK_SECRET`、`GITHUB_APP_CLIENT_ID`、`GITHUB_APP_CLIENT_SECRET`、`SESSION_SECRET`）。`RESEND_API_KEY` 刻意未設。

> ⚠️ **舊 App 勿用**：`yao-care-app`（App ID `3854967`，client_id `Iv23lit1XsR6Fe1vjBXy`）被其他專案共用，**已棄用**。`docs/SETUP-手動授權步驟.md` 與 admin spec 內仍引用舊 App 的值（見本頁末「已知文件不一致」），請以 `scope3esg` 為準。

### Repository permissions

| 權限 | 等級 | 為什麼 |
|------|------|--------|
| Administration | Read and write | 建 `scope3-inventory` repo |
| Contents | Read and write | 寫模板檔、commit `submissions.json`、寫 `config.yml` / `supplier-links.md` |
| Issues | Read and write | 開提交 Issue、加 label、留言 |
| Actions | Read and write | 租戶 repo 的 validate/calculate 等 workflow |
| Pages | Read and write | 部署儀表板 |
| Workflows | Read and write | 寫入 `.github/workflows/*.yml` 模板 |
| Metadata | Read-only | 基本 repo 中繼資料（GitHub 強制） |

### Organization permissions

| 權限 | 等級 | 為什麼 |
|------|------|--------|
| Members | Read-only | admin OAuth callback 驗證登入者是否為該 org active 成員 |

### Webhook 與 OAuth

- **Webhook URL** = `https://scope3-worker.lightman-chang.workers.dev/webhook`，Active 勾選，Secret = `GITHUB_WEBHOOK_SECRET`。
- **OAuth Callback URL** = `https://scope3-worker.lightman-chang.workers.dev/admin/callback`（admin 登入用，須在 App 設定的 user authorization callback 填入）。

### Events（Subscribe to events）

- **`installation` 事件無需訂閱**——GitHub 對 App 安裝/移除**自動送**，建 repo 就靠它。
- **`push` 事件不需訂閱**——本 App 刻意不訂 push（繞過難找的 Subscribe to events 區塊）。`config.yml` 改動改由租戶 repo 內的 `config-sync.yml` Action 主動 `curl` Worker 的 `/api/v1/config-sync/{org}`。
- 找不到「Subscribe to events」區塊？要先在 General 頁啟用 webhook（勾 Active）並 Save 權限，事件區才會出現（見 [03 案例 7](03-除錯指南.md)）。

## CI/CD

`.github/workflows/deploy.yml`，on push 到 `main` 觸發：

1. checkout
2. `pnpm install --frozen-lockfile`（working dir `scope3-worker`）
3. **`pnpm run build:templates`**（重新打包 `tenant-template/` → `src/templates/generated.ts`）
4. **`pnpm test`**（兩個 vitest pool：Cloudflare + Node）
5. `cloudflare/wrangler-action@v3` 部署

用到的 **GitHub repo secrets**：

| secret | 用途 |
|--------|------|
| `CLOUDFLARE_API_TOKEN` | wrangler-action 部署授權 |
| `CLOUDFLARE_ACCOUNT_ID` | 目標 Cloudflare 帳號（`9d9e58b5e0d1657b8f74bd2cbfc91ee3`） |

> ⚠️ **CI 不會自動套 D1 migration**。`wrangler deploy` 只部署 Worker 程式碼，不碰 D1 schema。新環境（或新增 migration 後）必須**手動**套：`wrangler d1 migrations apply scope3 --remote`。這是「安裝後 500 / `no such table: tenants`」最常見的根因——見 [04 套 D1 migration](04-維運操作.md) 與 [03 案例 1](03-除錯指南.md)。

## 開新環境檢查清單

從零開一套（或 disaster recovery）時依序確認：

1. **建 Cloudflare 資源**
   - [ ] D1 database（記下 database_id，填回 `wrangler.toml`）
   - [ ] R2 bucket `scope3-files`（R2 需先在 Dashboard 啟用，無 API——見 [03 案例 6](03-除錯指南.md)）
   - [ ] Queue `scope3-pull-jobs`
2. **套 D1 migration**（⚠️ CI 不做）
   - [ ] `wrangler d1 migrations apply scope3 --remote`
3. **設 Worker secrets**（6 個，`RESEND_API_KEY` 選用）
   - [ ] `GITHUB_APP_PRIVATE_KEY`（PKCS8）、`GITHUB_WEBHOOK_SECRET`、`GITHUB_APP_CLIENT_ID`、`GITHUB_APP_CLIENT_SECRET`、`SESSION_SECRET`
4. **GitHub App 設定**
   - [ ] Repository / Organization 權限如上表
   - [ ] Webhook URL + Secret（勾 Active）
   - [ ] OAuth Callback URL = `<WORKER_BASE_URL>/admin/callback`
   - [ ] vars `GITHUB_APP_ID` 填對 App ID
5. **設 GitHub repo secrets**（CI 用）
   - [ ] `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`
6. **部署並驗證**
   - [ ] `git push`（或 `wrangler deploy`）
   - [ ] `curl <WORKER_BASE_URL>/health` 回 `{ "status": "ok" }`
