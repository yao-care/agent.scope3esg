## 三層架構

這是一套多租戶 SaaS：一個 Cloudflare Worker 部署同時服務所有客戶 org，業務資料完全留在各客戶自己的 GitHub repo。

| 層 | 載體 | 存什麼 |
|----|------|--------|
| **L1 GitHub App（多租戶 SaaS 入口）** | GitHub App `scope3esg` | 安裝關係、權限。客戶安裝 App 即開通服務 |
| **L2 Cloudflare Worker（API 層）** | `scope3-worker`，程式碼在 `scope3-worker/src/` | **輕量設定**（D1：租戶、供應商 token）＋ **佐證檔**（R2） |
| **L3 租戶 repo（資料層）** | 各 org 的 `scope3-inventory` repo | **所有業務資料**：盤點設定、每筆碳排提交（Issue）、計算結果、儀表板、報表 |

**資料主權原則**：碳排業務資料（誰提交了什麼、算出多少 co2e、報表）全部在客戶自己的 GitHub repo，客戶完全掌握。Worker 只保留兩類資料：

- **D1**：輕量設定——租戶安裝對應（`tenants`）、供應商填表權杖（`supplier_tokens`）。
- **R2**：供應商上傳的佐證檔（發票、量測單等）。

Worker 不存任何碳排數值；所有數值都寫進租戶 repo 的 GitHub Issue 與 `data/submissions.json`。

## Worker 組件地圖

程式碼在 `scope3-worker/src/`。入口 `src/index.ts` 用 Hono 掛載所有路由，並匯出 `fetch`（HTTP）與 `queue`（佇列消費）兩個 handler。

### 路由（`src/routes/`，掛載點見 `src/index.ts`）

| 掛載路徑 | 檔案 | 職責 |
|----------|------|------|
| `/webhook` | `webhook.ts` | 接 GitHub webhook，驗 HMAC 簽章後分派 `installation` / `push` / `ping` 事件 |
| `/health` | `health.ts` | 健康檢查，回 `{ status: "ok", version: "1.0.0" }` |
| `/api/v1/upload` | `upload.ts` | 供應商佐證檔上傳到 R2（`POST /:org/:token`，驗 token、限 10MB） |
| `/api/v1/submit` | `api-submit.ts` | Push API 提交管道（Bearer token + `X-Scope3-Org` header，收 JSON） |
| `/api/v1/config-sync` | `config-sync.ts` | 由租戶 repo 的 `config-sync.yml` Action 呼叫（`POST /:org`），觸發供應商 token 同步 |
| `/submit` | `submit.ts` | Web Form 提交管道——serve 填表 HTML（`GET /:org/:token`）並處理表單 POST，含佐證檔上傳 |
| `/admin` | `admin.ts` | ESG Manager 管理頁 HTML 與 GitHub OAuth 登入流程（`/:org`、`/:org/login`、`/callback`、`/:org/logout`） |
| `/api/v1/admin` | `admin-api.ts` | 管理 API（讀寫 config、供應商連結、提交狀態），皆需有效 session 且 org 相符 |

### Handlers（`src/handlers/`，被路由與佇列呼叫的業務邏輯）

| 檔案 / 函式 | 職責 |
|-------------|------|
| `installation.ts` → `handleInstallation` | 安裝事件（action=created）→ 取 installation token → `createTenantRepo` 建 repo → `insertTenant` 寫 D1 |
| `submission.ts` → `processSubmission` | 三管道共用的提交核心：驗 token/有效期、查租戶、建 GitHub Issue。回 `{ success, issueNumber }` |
| `config-push.ts` → `handleConfigPush` / `syncConfig` | `handleConfigPush`：push webhook 時若 `config.yml` 有改才呼叫 `syncConfig`。`syncConfig`：讀 `config.yml` → 為新供應商產 token 寫 D1（選用寄信）→ 重建 `supplier-links.md`。**被 webhook push 與 `/api/v1/config-sync` 共用** |
| `pull-job.ts` → `executePullJob` | Pull 管道：向供應商 API 抓資料 → 轉交 `processSubmission`（channel=`pull`） |

### Lib（`src/lib/`，純函式工具）

| 檔案 | 職責 |
|------|------|
| `tokens.ts` | 產供應商權杖（`stok_` + 32 bytes hex）、組填表網址 `{base}/submit/{org}/{token}`、算到期日 |
| `session.ts` | 無狀態 HMAC-SHA256 簽章（`base64url(JSON).base64url(HMAC)`），用於 admin session cookie 與 OAuth state |
| `config-yaml.ts` | `config.yml` 的 JSON ↔ YAML 轉換與結構正規化（admin 存設定用） |

### GitHub 整合（`src/github/`）

| 檔案 | 職責 |
|------|------|
| `app.ts` | 用 `@octokit/app` 建 App 實例、取 installation token（`getInstallationOctokit`） |
| `repo.ts` → `createTenantRepo` | 建 `scope3-inventory` repo、寫入模板檔（`TENANT_FILES`）、建 22 個 label（status/validation/cat 1-15）。**遇 422（repo 已存在）改 GET node_id，冪等跳過寫入** |
| `issue.ts` → `createSubmissionIssue` | 把一筆提交寫成 GitHub Issue（含人類可讀表格 + 機器可讀 `scope3-data` JSON 區塊） |
| `config.ts` → `readTenantConfig` | 讀租戶 repo `config.yml` 並用 js-yaml 解析成 `TenantConfig` |
| `supplier-links.ts` | 組 `supplier-links.md` 表格、寫回租戶 repo（`upsertSupplierLinks`） |

### Queue 與 Email

| 檔案 | 職責 |
|------|------|
| `queue/consumer.ts` → `handleQueue` | 消費 `scope3-pull-jobs` 佇列訊息，逐筆呼叫 `executePullJob`，成功 `ack`、失敗 `retry` |
| `email/resend.ts` → `sendOnboardingEmail` | 用 Resend 寄供應商邀請信。**僅在 `RESEND_API_KEY` 有設時才呼叫**；未設則整段跳過（目前刻意未設，改手動遞送連結） |

### 中介層

- `middleware/github-webhook.ts` → `verifyGitHubWebhook`：驗 `x-hub-signature-256` HMAC-SHA256；失敗回 401。

## 租戶 repo 結構

租戶 repo 檔案的**單一事實來源**是 `scope3-worker/tenant-template/`。改完要跑 `pnpm run build:templates` 打包成 `src/templates/generated.ts`（已 commit），由 `createTenantRepo` 在建 repo 時逐檔 commit 到租戶 repo。

| 檔案 | 職責 |
|------|------|
| `config.yml` | 租戶盤點設定：`inventory_year`、`enabled_categories`（Scope 3 的 15 類）、`suppliers[]`（id/name/contact/pull_api/pull_schedule） |
| `data/emission-factors.json` | 排放係數表（活動類型 → 係數值 + 單位）。calculate 階段據此算 co2e |
| `scripts/lib.mjs` | 純驗證/計算演算法（`UNIT_RULES`、`validateUnit`、`matchFactor`、`calculateCo2e`）。同時被 Action runner 與 worker 單元測試使用 |
| `scripts/validate.mjs` | issue opened/edited 時跑：解析 `scope3-data`，驗單位/異常值/缺件，留言並視情況加 `validation:error` label |
| `scripts/calculate.mjs` | issue 加 `status:approved` label 時跑：讀 `scope3-data` → 匹配係數 → 算 co2e → 更新 `data/submissions.json` → 留言 |
| `scripts/report.mjs` / `report-lib.mjs` | 讀 `submissions.json` 產 `reports/` 下 CSV 與 GHG Protocol Markdown |
| `docs/index.html` / `dashboard.js` / `aggregate.mjs` | GitHub Pages 儀表板：`aggregate.mjs` 彙整 KPI（總量、依類別/活動/供應商），前端呈現 |
| `.github/workflows/validate.yml` | on `issues: [opened, edited]` → 跑 validate.mjs |
| `.github/workflows/calculate.yml` | on `issues: [labeled]`，僅 `status:approved` → 跑 calculate.mjs，commit `submissions.json` |
| `.github/workflows/pages.yml` | on push `data/submissions.json` 或 `docs/**` → 部署儀表板到 Pages |
| `.github/workflows/report.yml` | `workflow_dispatch` 或每月排程（cron `0 1 1 * *`）→ 產報表並建 Release |
| `.github/workflows/config-sync.yml` | on push `config.yml` → `curl POST` Worker `/api/v1/config-sync/{org}` |
| `.github/ISSUE_TEMPLATE/scope3-submission.yml` | 手動開 Issue 提交的範本 |

## 核心資料流

從安裝到報表的完整流程（文字編號，避免 mermaid 在 terminal 看不到）：

1. **安裝 → 建 repo**：客戶在 GitHub org 安裝 App `scope3esg` → GitHub 自動送 `installation`（action=created）webhook 到 `/webhook` → `handleInstallation` 取 installation token → `createTenantRepo` 建 `scope3-inventory`（寫入全部模板檔 + labels）→ `insertTenant` 把 `installation_id / org / repo_node_id` 寫進 D1。

2. **供應商提交 → GitHub Issue**：供應商經三管道之一提交 → `processSubmission` 驗 token、查租戶 → `createSubmissionIssue` 開一個 Issue。**每個 Issue body 同時含人類可讀表格與一段機器可讀區塊**：

   ```
   <!-- scope3-data:
   { ...JSON... }
   -->
   ```

   ⚠️ **這是關鍵接縫**：由 `src/github/issue.ts` 以 `JSON.stringify(submission, null, 2)` 寫入（前後各一行換行），由 `validate.mjs` / `calculate.mjs` 用 regex `/<!-- scope3-data:\n([\s\S]*?)\n-->/` 讀回。**寫入格式（換行位置、註解標記）與讀取 regex 必須完全一致**，任一邊改動都會讓另一邊解析不到資料。Issue 開出時即帶 `status:submitted` 與 `cat:{N}` label。

3. **驗證 Action**：`validate.yml` 在 issue opened/edited 觸發 → `validate.mjs` 解析 `scope3-data`、驗單位/異常值/缺件 → 留言結果，有問題時加 `validation:error`。

4. **審核**：ESG Manager 在 GitHub Issues / 看板審核，核定後手動加 `status:approved` label（審核動作目前在 GitHub 端進行，不在 admin UI）。

5. **計算 Action**：`calculate.yml` 在 issue `labeled` 且 label 為 `status:approved` 時觸發 → `calculate.mjs` 讀 `scope3-data` → `matchFactor` 配 `emission-factors.json` 的係數 → `calculateCo2e` 算排放量 → 更新 `data/submissions.json` → commit + push → 留言結果。

6. **儀表板 / 報表 Action**：`submissions.json` 一被 push，`pages.yml` 觸發部署 GitHub Pages 儀表板；`report.yml` 依排程或手動觸發產 CSV/Markdown 報表並建 Release。

## 三個供應商提交管道

三管道最終都匯流到 `processSubmission`（`src/handlers/submission.ts`），差別只在入口與驗證方式：

| 管道 | 入口 | 身分驗證 | 適用 |
|------|------|----------|------|
| **Web Form** | `GET/POST /submit/:org/:token` (`submit.ts`) | 網址內的 supplier token | 供應商手動填表，可附佐證檔 |
| **Push API** | `POST /api/v1/submit` (`api-submit.ts`) | `Authorization: Bearer <token>` + `X-Scope3-Org` header | 供應商系統主動推送 JSON |
| **Pull Job** | 佇列消費 `executePullJob` (`pull-job.ts`) | 用 token 向供應商 API 抓 | 由 Worker 定時向供應商 API 拉取 |

> ⚠️ **Pull Job 現況**：消費端（`handleQueue` → `executePullJob`）與 `scope3-pull-jobs` 佇列、`pull_jobs` D1 表都已就位，但目前**程式碼中沒有任何地方往 `SUBMISSION_QUEUE` 送訊息**（無 `.send()`、`wrangler.toml` 也無 cron `[triggers]`）。也就是說 Pull 管道的消費邏輯已完成，但「定時把工作排進佇列」的觸發端尚未啟用。實際運作的是 Web Form 與 Push API 兩管道。

## 管理介面（admin）

ESG Manager（業務人員，非工程師）用 `/admin/:org` 網頁管理盤點設定與供應商，不需直接編輯 repo 裡的 `config.yml`。

- **登入**：GitHub OAuth。`/admin/:org` 無 session 導向 `/admin/:org/login` → GitHub 授權 → `/admin/callback` 驗 `state` 簽章、換 user token、確認登入者為該 org active 成員（非成員 403）→ 發無狀態 session cookie（HMAC 簽章、HttpOnly/Secure、8 小時）。
- **管理 API**（`/api/v1/admin/:org/*`，皆需 session 且 org 相符）：讀寫 `config.yml`（存檔後觸發 `syncConfig` 產 token）、供應商連結一覽（查 D1）、提交狀態（查 repo issues）。

細節見 [02 · 環境與設定](02-環境與設定.md) 與 `docs/superpowers/specs/2026-05-26-scope3-admin-ui-design.md`。

## 多租戶模型

- **一個 Worker 部署服務所有 org**，不為每個客戶開獨立部署。
- 以 GitHub `installation_id` / `org` 區分租戶。webhook 與管理 API 都帶 org，據此查 D1 `tenants` 表取得對應的 `installation_id`，再換成該租戶的 installation token 去操作其 repo。
- D1 `tenants` 表是租戶目錄：`installation_id`（主鍵）、`org`、`repo_node_id`、`created_at`。
- 跨租戶隔離靠：供應商 token 綁 org（`processSubmission` 會比對 `tokenRow.org === input.org`）、admin session 綁 org（cookie org 須與路徑 org 相符）。
