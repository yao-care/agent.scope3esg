# 04 · 維運操作

> 日常操作的步驟與可複製指令。系統壞了看 [03](03-除錯指南.md)，設定看 [02](02-環境與設定.md)，架構看 [01](01-系統架構.md)。

> **通用提醒**
> - wrangler 指令前帶 token：`CLOUDFLARE_API_TOKEN=<token> pnpm wrangler ...`（token 由使用者提供，`cfat_` 開頭）。
> - 這台機器對外網路**不穩**，wrangler / gh / curl 單次失敗（404/EOF/ECONNRESET）常是假象。包重試迴圈，並在工具呼叫時加 `dangerouslyDisableSandbox: true`（沙箱會擋對外連線）。重試樣板：`n=0; until <cmd>; do n=$((n+1)); [ $n -ge 8 ] && break; sleep 3; done`。
> - 套件管理一律 **pnpm**（不用 npm）。
> - 所有 wrangler 指令在 `scope3-worker/` 目錄下執行。

## 部署

兩種方式（擇一）：

```bash
# 方式 A：push 觸發 CI（推薦）。CI 會跑 build:templates + pnpm test 再 deploy。
git add -A && git commit -m "..." && git push   # main 分支（本專案直接在 main 開發）

# 方式 B：手動部署（繞過 CI 測試，謹慎用）
cd scope3-worker
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler deploy
```

部署後驗證：

```bash
curl https://scope3-worker.lightman-chang.workers.dev/health   # 應回 {"status":"ok","version":"1.0.0"}
```

## 套 D1 migration

⚠️ **CI 不會自動套**。新增 migration 或開新環境後必須手動執行（否則安裝 webhook 會 `no such table: tenants` → 500，見 [03 案例 1](03-除錯指南.md)）。

```bash
cd scope3-worker
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler d1 migrations apply scope3 --remote
```

migration 檔在 `scope3-worker/migrations/`（目前 `0001_initial.sql`，建 4 張表）。

## 查 D1

```bash
cd scope3-worker
# 租戶目錄（installation_id / org / repo_node_id）
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler d1 execute scope3 --remote \
  --command "SELECT * FROM tenants"

# 供應商填表權杖
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler d1 execute scope3 --remote \
  --command "SELECT token, org, supplier_id, expires_at FROM supplier_tokens WHERE org='yao-care'"
```

D1 共 4 張表（schema 見 `migrations/0001_initial.sql`）：

| 表 | 內容 | 現況 |
|----|------|------|
| `tenants` | 租戶安裝對應（`installation_id` PK、`org`、`repo_node_id`、`created_at`） | 使用中 |
| `supplier_tokens` | 供應商填表權杖（`token` PK、`org`、`supplier_id`、`expires_at`、`created_at`） | 使用中 |
| `pull_jobs` | Pull 管道排程（`job_id`、`org`、`supplier_id`、`api_url`、`schedule`、`last_run_at`） | **使用中**：`syncConfig` 對含 `pull_api` 的供應商 `upsertPullJob` 寫入；cron 觸發的 `handleScheduled` 以 `listAllPullJobs` 讀取、`touchPullJobLastRun` 更新 |
| `audit_log` | 稽核記錄（`id`、`org`、`action`、`actor`、`target`、`created_at`） | **使用中**：`insertAuditLog` 記錄三種操作——`app_installed`（安裝）、`submission_created`（提交成功）、`config_synced`（設定同步）；`listAuditLogByOrg` 可查詢 |

> 加 `--json` 在網路不穩時較好解析。`pull_jobs` 在有 `pull_api` 供應商完成 config 同步後才有資料；`audit_log` 隨安裝 / 提交 / 設定同步累積記錄。

## 設定 / 輪換 secret

```bash
cd scope3-worker
# 設定或更新（互動式貼上值，或用 pipe）
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler secret put SESSION_SECRET

# private key 從檔案 pipe（必須先轉 PKCS8，見 03 案例 2）
cat pkcs8.pem | CLOUDFLARE_API_TOKEN=<token> pnpm wrangler secret put GITHUB_APP_PRIVATE_KEY

# 列出已設的 secret（只看名稱，看不到值）
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler secret list
```

secret 清單與用途見 [02 · Worker secrets 一覽表](02-環境與設定.md)。

## 跑測試

```bash
cd scope3-worker
pnpm test          # = test:cf（Cloudflare pool）+ test:node（Node pool），兩個都要過
pnpm run test:cf   # 只跑 Cloudflare workers pool
pnpm run test:node # 只跑 Node pool（純函式：session、config-yaml、lib.mjs 等）
```

CI 部署前會跑 `pnpm test`，本機改完也應跑過再 push。

## 改租戶模板

租戶 repo 檔案的單一事實來源是 `scope3-worker/tenant-template/`。流程：

```bash
cd scope3-worker
# 1. 編輯 tenant-template/ 下的檔案（config.yml、scripts/*.mjs、workflows、docs/...）
# 2. 重新打包成 src/templates/generated.ts
pnpm run build:templates
# 3. commit 產生的 generated.ts（已納入版控）
git add tenant-template/ src/templates/generated.ts && git commit -m "chore: update tenant template"
# 4. push 觸發部署（或手動 deploy）
git push
```

> ⚠️ **既有租戶 repo 不會自動補新檔**：`createTenantRepo` 對「已存在的 repo」是冪等跳過，只在**首次建 repo** 寫入模板。在 `tenant-template/` 新增的檔案，既有租戶 repo 需**手動補**（用 `gh api PUT contents`）——見 [03 案例 5](03-除錯指南.md)。

## 新增租戶

正常情況**全自動**，使用者只需安裝 App：

1. 客戶在其 GitHub org 安裝 App `scope3esg`。
2. GitHub 自動送 `installation` webhook → Worker `handleInstallation` 建 `scope3-inventory` repo、寫 D1。

**前提**：production D1 必須已套 migration（否則建 repo 那步後 `insertTenant` 失敗 → 500，repo 可能已建但租戶沒入庫）。見 [03 案例 1](03-除錯指南.md)。

驗證新租戶：

```bash
cd scope3-worker
CLOUDFLARE_API_TOKEN=<token> pnpm wrangler d1 execute scope3 --remote \
  --command "SELECT * FROM tenants WHERE org='<新org>'"
```

首次設定 App / 資源的逐步指引見 `docs/SETUP-手動授權步驟.md`（注意該文件引用的是舊 App，值以 `CLAUDE.md` / [02](02-環境與設定.md) 為準）。

## 重新觸發 installation（修復用）

安裝當下若因 migration 未套等原因失敗，**不需請使用者重裝 App**。有 `GITHUB_WEBHOOK_SECRET` 即可自簽 HMAC 重送一次 `installation` 事件，讓 Worker 重跑 `handleInstallation`（建 repo 與 insertTenant 皆冪等，重跑安全）。

完整腳本見 [03 通用除錯工具 C](03-除錯指南.md)。

## 更新排放係數

排放係數在租戶 repo 的 `data/emission-factors.json`（活動類型 → 係數值 + 單位）。calculate 階段據此算 co2e。

- **改既有租戶**：直接編輯該租戶 repo 的 `data/emission-factors.json` 並 commit（可用 `gh api PUT contents` 或 repo 內 PR）。
- **改未來新租戶的預設值**：編輯 `scope3-worker/tenant-template/data/emission-factors.json` → `pnpm run build:templates` → commit `generated.ts` → 部署（只影響之後新建的 repo）。

> ⚠️ 改係數時注意單位一致性：`emission-factors.json` 的分母 `unit`、`scripts/lib.mjs` 的 `UNIT_RULES`、`src/routes/submit.ts` 表單單位選項三者的 activity_type 與單位要對齊，否則計算階段「單位無法轉換」——見 [03 案例 9](03-除錯指南.md)。

## 檢視供應商連結

每家供應商的專屬填表連結（`{WORKER_BASE_URL}/submit/{org}/{token}`）有兩個檢視點：

- **租戶 repo 的 `supplier-links.md`**：由 `syncConfig` 自動產生維護（機密，僅 private repo 內共享）。

  ```bash
  gh api /repos/<org>/scope3-inventory/contents/supplier-links.md \
    --jq '.content' | base64 -d
  ```

- **admin UI**：`/admin/:org` 的「連結一覽」區塊（GitHub 登入後）。

連結未產生 / 未更新（改 `config.yml` 後沒反應）的排查見 [03 案例 8](03-除錯指南.md)。
